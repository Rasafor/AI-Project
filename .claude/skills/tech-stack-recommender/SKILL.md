## Description

**Purpose:** A system architecture names components ("Genealogy Engine," "Local Persistent Store") but not the actual technology that would build them. This Skill closes that gap: it reads an existing architecture and, for every component, recommends one real, current, named technology — rated honestly for how well it fits *this* idea's actual scale, not a generic best-practice default.

**When to use it:** Use when the user already has (or has just had generated by `/system-architect`) a `project-blueprint/architecture.md` and asks what to actually build it with — e.g., "what tech stack fits this?", "recommend technologies for each piece," "what should I use for the database?"

**When NOT to use it:** Do not use this to design the architecture itself — that's `/system-architect`'s job, and this Skill depends on its output existing first. Do not use it for general technology opinions unrelated to a specific saved architecture.

**Who it's for:** The same non-technical-to-technical spectrum of users as `/system-architect` — people who need to walk into a "what should I build this with?" conversation (with a developer, an AI coding agent, or themselves) already knowing the shape of the answer.

## Instructions

### Inputs needed
- `project-blueprint/architecture.md` must already exist. If it doesn't, tell the user to run `/system-architect` first — do not invent an architecture to fill the gap.

### Steps

1. **Read `project-blueprint/architecture.md` in full**, especially the Components table and the "Why it exists" column for each — that column is what tells you the real scale and constraints (single device vs. shared/cloud, how much data, how much traffic, real-time or not), not just the component's label.

2. **For each component, recommend exactly one real, currently-maintained technology** — a specific named product, library, framework, or service (e.g. "SQLite," "Postgres," "React + TypeScript," "IndexedDB via Dexie.js"), never a category placeholder like "a database" or "a frontend framework."

3. **Rate the fit of every recommendation honestly**, using:
   - 🟢 **great fit** — matches this idea's actual scale and needs well, no meaningful compromise
   - 🟡 **good fit** — works, but there's a real tradeoff worth knowing about
   - 🔴 **consider carefully** — the pragmatic/common choice, but genuinely mismatched to this idea's scale (over- or under-built) and the user should know why before committing

   Do not default every row to 🟢. A rating is only useful if it's calibrated to *this* idea — e.g., a cloud-scale distributed database is 🔴 for a single-device offline app even if it's a fine database in general. If nothing in the stack warrants 🟡 or 🔴, double-check you're actually reasoning about scale and not just listing popular defaults.

4. **Write the "why" as one plain-English sentence per row.** No jargon without a same-sentence, few-word definition (e.g., "an ORM (a tool that lets code talk to the database without writing raw SQL)"). A non-technical reader should be able to read the sentence once and understand the choice.

5. **Format as a table**, one row per component, columns: Component | Recommended Technology | Fit | Why | Learn More. Icons and short labels only — no paragraphs of prose outside the table. This must be scannable in under a minute.

6. **Give each row a copy-ready follow-up prompt** the user could paste into a later conversation to learn more about that specific technology, in the format of: *"Explain [Technology] to me like I'm new to [general category], using my [project idea] as the example."* Put it in the "Learn More" column as inline code so it's copy-paste ready as-is.

7. **Save the result** to `project-blueprint/tech-stack.md`, containing, in order:
   - A title and one-line note that this maps to `project-blueprint/architecture.md`
   - The full recommendation table (Steps 5–6)
   - A closing fit-rating summary line: count of 🟢, 🟡, and 🔴 across all rows

   If `project-blueprint/tech-stack.md` already exists and its contents look like they belong to a different, unrelated project, check with the user before overwriting it.

8. **Report back to the user**: the exact file path (`project-blueprint/tech-stack.md`), and the fit-rating breakdown — how many 🟢 / 🟡 / 🔴 total.

### Expected output
A file at `project-blueprint/tech-stack.md`: one table row per architecture component, each with a specific named technology, an honest 🟢/🟡/🔴 fit rating calibrated to this idea's real scale, a one-sentence plain-English reason, and a copy-ready "learn more" prompt. The calling response states the file path and the fit-rating counts.

### Things to avoid
- Do not recommend a generic "safe default" stack disconnected from the architecture's actual scale (e.g., don't recommend a microservices/Kubernetes setup for a single-user local app, or a single SQLite file for something the architecture describes as multi-user and concurrent).
- Do not rate every recommendation 🟢 — that signals the fit rating wasn't actually evaluated against this idea's scale.
- Do not recommend a category ("a database," "a cloud provider") instead of one real, named, current technology.
- Do not write dense paragraphs — the whole point is a scannable table, not a wall of text.
- Do not leave jargon undefined — every technical term gets a same-sentence plain-language gloss the first time it appears in a row.
- Do not skip the "Learn More" prompt for any row, and do not write it as a general question — it must reference this specific project/idea.
