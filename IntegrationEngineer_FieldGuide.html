Integration Engineer Field Guide

Built for learners in the Colaberry Enterprise AI Leadership Accelerator who are becoming AI Solution Architects. You will not hand-wire every API call yourself — AI will draft most of the integration code and contracts. Your job is to know enough integration engineering to direct, evaluate, and approve what the AI produces: the seams between systems, not the systems themselves. This guide teaches that discipline, then applies it end-to-end against one realistic initiative connecting six independently-owned systems.

The Discipline

Why Integration Engineering Exists

An AI agent can wire a REST call to almost any service in minutes: read the vendor’s docs, write a client, parse the response. What it cannot yet reliably do is guarantee that call still behaves correctly the day the vendor has an outage, the day a network blip turns a payment confirmation into a mystery, or the day someone double-clicks submit. That gap — between an integration that works in a demo and one that survives a bad Tuesday in production — is why integration engineering exists, and it is exactly the gap an AI Solution Architect is paid to close before approving AI-generated integration code.

Integration engineering is the discipline of connecting independently-owned systems — each with its own uptime, its own rate limits, its own failure modes, and often its own vendor with its own incentives — into one reliable pipeline, without any single seam becoming the reason the whole system goes down. Skipping it does not remove the risk; it moves the cost of discovering a missing timeout or a missing idempotency key from a code review to a production incident, a duplicate payment, or a claimant who never got notified.

What happens without it

An AI agent is asked to “connect claim intake to the fraud-scoring vendor.” It writes a clean synchronous POST call that works perfectly against the vendor’s sandbox. Nobody specified a timeout, a retry cap, or what happens when the vendor is degraded instead of down. One Tuesday the vendor’s API slows to nine-second responses instead of failing outright — and because nothing in the code says “stop waiting,” the entire claims pipeline backs up behind it, one request at a time, until every claimant in the queue is stuck, not just the ones actually affected by the slow vendor.

As an AI Solution Architect, you sit between the systems your business already owns, the AI services you are adding, and the vendors you don’t control. Integration engineering is your shared vocabulary with all three — the thing that lets you catch a fragile seam before it becomes a production incident.

The Discipline

The 20% an Integration Engineer Must Know

You do not need to become a full-time integration engineer. You need the subset of the discipline that lets you evaluate AI-generated integration code critically. That subset is ten ideas.

1. REST vs. GraphQL vs. event-driven APIs

REST exposes resources at fixed URLs with standard HTTP verbs — simple, cacheable, and the default choice for most system-to-system integration. GraphQL lets the caller specify exactly which fields it wants in a single request — valuable when a client (like a dashboard) needs to compose data from many resources and wants to avoid round-trips or over-fetching, at the cost of a more complex server and harder-to-cache responses. Event-driven APIs (a message broker or event stream) decouple the producer from the consumer entirely — the producer doesn’t call anyone, it just publishes, and any number of consumers can react independently. An AI agent will often default to REST for everything because it’s the most-trained-on pattern; an architect’s job is to ask whether the interaction is actually a request-for-an-answer (REST), a flexible-read (GraphQL), or a fact-that-happened (event).

StyleBest fit when…Watch out for…
RESTA caller needs a specific answer now, or is writing/changing stateChatty APIs that force many round-trips for one screen or decision
GraphQLA client composes data from many resources and over-fetching is expensiveCaching and rate-limiting are harder; a single query can hide a very expensive server-side cost
Event-drivenWork is naturally asynchronous, multiple consumers need the same fact, or volume is burstyHarder to trace a single request end-to-end; requires a broker someone must operate

2. API contracts & versioning

A contract is a promise about shape: which fields exist, their types, which are required, and what every error looks like. AI-generated integration code is very good at making a contract that works today and silent about what happens when it must change. The discipline: version explicitly (URI versioning — /v1/, /v2/ — is the simplest to reason about), treat additive changes (a new optional field, a new endpoint) as non-breaking, and treat anything else — a removed field, a changed type, a renamed enum value — as breaking and requiring a new version with a published deprecation window. A contract that can change silently underneath its consumers is not a contract.

Not a contract

“The API returns claim data as JSON.”

A contract

“POST /v1/fnol returns 202 with {claimId: string(UUID), confirmationNumber: string, status: enum}. Field removal or type change requires /v2/ and a 6-month Sunset window on /v1/.”

3. Authentication: keys, OAuth, and tokens

Not every integration needs the same authentication weight. A static API key is simple and appropriate for low-sensitivity, machine-to-machine calls to a vendor that doesn’t support anything richer — common with legacy systems. OAuth 2.0 client-credentials is the standard for machine-to-machine calls that need scoped, rotatable, short-lived access without a human in the loop. OAuth 2.0 authorization-code with PKCE is for when a human is actually present (a claimant logging into a portal) and the system needs to act on their behalf. HMAC request/webhook signing proves a payload wasn’t tampered with in transit and is the standard way to authenticate an inbound webhook, since the caller (the vendor) can’t easily hold your OAuth credentials. Whichever mechanism is used, the same rule applies everywhere: credentials never appear in a URL, a query string, or a log line.

4. Webhooks vs. polling

A webhook is the far system calling you back when something is ready — low latency, low wasted traffic, but you must expose a reachable, authenticated endpoint and handle the case where the callback never arrives. Polling is you repeatedly asking “is it ready yet” — simple and resilient to a missed callback, but wastes calls and adds latency proportional to your poll interval. The pattern that survives production is usually a hybrid: treat the webhook as the primary, low-latency path, and fall back to polling only if the webhook hasn’t arrived within a defined SLA. Neither alone is complete — a webhook-only integration has no recovery path when a callback silently drops.

5. Idempotency, retries & backoff

An operation is idempotent if doing it twice produces the same end state as doing it once. Reads (GET) are naturally idempotent. Writes are not, unless you make them so — typically with an Idempotency-Key header: a client-generated identifier that the receiving system stores and checks before processing, so a retried request with the same key returns the original result instead of repeating the side effect. This is what makes retrying safe. A retry should never be unbounded: cap the attempt count, and space attempts out with exponential backoff (each wait roughly doubles) plus a small amount of random jitter, so a fleet of retrying clients doesn’t all hammer the recovering dependency at the same instant.

6. Timeouts & circuit breakers

Every outbound call needs an explicit timeout — a promise to stop waiting, not just a hope that the other side responds quickly. Without one, a single slow dependency can exhaust every thread or connection in your service, taking down everything else it touches. A circuit breaker goes one step further: after a defined number of failures in a window, it stops calling the failing dependency entirely (the circuit is open) for a cooldown period, then allows a single test call through (half-open) before fully resuming (closed). The point of both is the same — fail fast and visibly, instead of failing slowly and invisibly.

7. Data mapping & transformation

No two systems agree on field names, units, or enums, and an AI agent will happily map fields by guessing at similar names without checking that a legacy status code of “A” and a canonical enum of ACTIVE actually mean the same thing in every case. Every target field in a data mapping must be traceable to exactly one source field and one stated transformation — unit conversion, date/timezone normalization, currency parsing, enum translation — and an unmapped or out-of-range source value should be flagged, never silently defaulted or dropped.

8. Rate limits

Most external APIs enforce a rate limit — a cap on requests per second or per minute — and will return 429 Too Many Requests, often with a Retry-After header, when you exceed it. The mature pattern is defensive on both ends: throttle your own outbound traffic with a local rate limiter (commonly a token bucket) so you rarely trip the vendor’s limit in the first place, and when you do get a 429, honor the Retry-After value instead of guessing your own backoff.

9. Error handling & dead-letter queues

Every integration will eventually receive a request or event it cannot process — malformed, permanently rejected by a downstream system, or exhausted of retries. A dead-letter queue (DLQ) is where that failure goes instead of disappearing: a durable store holding the original payload, the error, the attempt count, and a correlation ID, so a human can triage and replay it later. An integration with no DLQ doesn’t have fewer failures — it just loses them silently.

10. Synchronous vs. asynchronous integration

Use synchronous calls when a human or another process is actively waiting for the answer before it can proceed — a coverage check before a claim is accepted, a fraud score before a payout decision. Use asynchronous delivery (events, queues, webhooks) when the work can happen in the background, volume is bursty, or multiple independent consumers need the same fact. Most real integration landscapes, including this guide’s example, are a deliberate mix of both — never chosen by default, always justified by whether something is actually waiting on the answer.

The Discipline

Good vs. Bad Integration

Every AI-drafted integration should pass a review before an architect approves it: does every external call have a timeout, is every retry capped and backed off, does every write carry an idempotency key, is the contract versioned, and does a failing dependency have a fallback or a dead-letter path instead of taking down everything around it. The Discipline

KPIs & Integration Metrics

An integration without KPIs behind it is a diagram, not a system you can operate. Six metrics matter most. Integration success rate — the percentage of calls that complete successfully, first try or after a legitimate retry. Latency at p50/p95/p99 per seam — because a single average hides the slow tail that actually causes SLA breaches. Retry recovery rate — how much of your failure volume a capped retry actually rescues, versus how much falls through to a fallback or a dead letter. DLQ depth — a trend, not a snapshot; a DLQ that only grows means failures are being caught but never resolved. Contract test coverage — the percentage of consumer-provider pairs protected by an automated contract test that would fail a build on a breaking change. Rate-limit incident count — how often you actually trip a vendor’s throttle, which should trend toward zero as client-side limiting matures. When you review an AI-generated integration, insist on the same three things for every seam: a baseline, a target, and a verification method — see the KPI tiles and charts in the Integration Architecture and Error-Handling documents.

The Integration Engineer’s Review Lens

When an AI agent hands you an integration artifact, run this checklist before you approve it. This is the actual lens applied to every document in this guide.

CheckQuestion to askRed flag
Timeout presenceDoes every external call declare an explicit timeout?An HTTP client configured with no timeout, or a default of “whatever the library ships with”
Retry boundednessIs every retry capped with backoff, and does it distinguish retryable from non-retryable errors?An infinite retry loop, or code that retries a 400 validation error as if it were a 503
IdempotencyDoes every write carry an idempotency key, and is it actually checked server-side, not just generated and ignored?A payment, disbursement, or state-changing endpoint with no idempotency key at all
Circuit breaker / fallbackDoes a failing dependency get isolated, with a defined fallback, instead of cascading?No circuit breaker on a dependency that sits in the synchronous, human-facing critical path
Contract versioningIs the contract versioned, and is a breaking change actually flagged as breaking?An unversioned API, or a “minor” release that silently removes or retypes a field
Error taxonomyDoes every error response carry a stable, documented code and a correlation ID?A generic 500 with no error code, no correlation ID, and a raw stack trace in the body
Dead-letter handlingDo unresolvable failures land somewhere a human can find and replay them?A failed webhook delivery or event that is logged once and then gone
Secret hygieneDo URLs, logs, and error messages avoid ever containing a secret, key, or token?An API key visible in a query string, a signed URL logged in full, or a token in a stack trace
Rule of thumb

If you cannot point to the timeout, the retry cap, and the idempotency key for a given write, the integration is not ready to approve — regardless of how clean the happy-path demo looks.

1. Purpose & Scope

This specification is the contract of record for the Claims Integration Hub’s public API (consumed by the ClaimsPilot Claimant Portal and the Adjuster/SIU Workbench) and for the five outbound integrations the Hub owns. It is written OpenAPI-style: every endpoint states its method, path, authentication, request/response schema, and error behavior.

2. Versioning Policy

  • URI versioning — /v1/, /v2/. A version number never changes meaning inside itself.
  • Additive changes (a new optional field, a new endpoint) ship without a version bump.
  • Breaking changes (a removed/renamed field, a changed type, a changed auth requirement) require a new version, a minimum 6-month deprecation window on the prior version, and a Sunset HTTP header on every response served from the deprecated version.
  • Every consumer — the Claimant Portal, the Adjuster Workbench, and the Hub’s own five outbound clients — is covered by a consumer-driven contract test that fails the build if a provider ships a breaking change without a version bump.

Sequence Diagrams

ClaimsPilot AI — Four Flows: Happy Path, Async Extraction, Retry, and Failure Branch

Meridian Mutual Insurance

Document IDSEQ-MM-2026-001
Version1.0
OwnerPriya Nandakumar
StatusApproved
Date2026-09-08

1. Purpose

A sequence diagram that only shows the happy path is not a complete integration design — it says nothing about what happens when a call is slow, fails, or needs to be retried. This document specifies four flows: the standard straight-through path, the asynchronous extraction pattern (webhook with polling fallback), an explicit retry path against a transient failure, and a failure branch showing a circuit breaker in the open state.

2. Flow A — Happy Path: Straight-Through Settlement

A low-complexity claim, all six seams succeed on the first attempt, and the claim settles without human intervention.

3. Flow B — Asynchronous Document Extraction (Webhook with Polling Fallback)

Lumina’s extraction jobs typically complete in 10–45 seconds. The webhook is the primary, low-latency path; if no callback arrives within the 120-second SLA, the Hub falls back to polling every 15 seconds for up to 5 minutes. The Hub deduplicates on jobId regardless of which path resolves first — whichever arrives second is a no-op.

4. Flow C — Retry Path: Payment Gateway Transient Failure

SettleFlow returns two consecutive 503 responses before succeeding on the third attempt. The same Idempotency-Key is sent on every attempt, so even if the first “failed” call had actually succeeded server-side, SettleFlow’s own dedupe guarantees exactly one disbursement.

5. Flow D — Failure Branch: Fraud-Scoring Circuit Breaker Open

SentinelRisk degrades to sustained timeouts. After the 8th failure inside a 60-second window, the circuit opens; the Triage Orchestrator stops calling SentinelRisk entirely and routes the claim to standard adjuster assignment instead of blocking on a dependency that has already proven itself unreliable.

6. Reading Notes

  • A dashed arrow is a response or an asynchronous callback; a solid arrow is a request.
  • Every write-path message in Flows A and C carries an idempotency key, even though the diagram labels abbreviate it for space — see the Error-Handling document for the full key scheme per seam.
  • Flow D does not represent an outage of the whole platform — only the straight-through capability is degraded; standard adjuster routing continues to function normally.

1. Purpose & Scope

No seam ships to pilot without evidence covering all six categories below, run against a sandboxed double of each external system (PAS-7, Lumina, SentinelRisk, SettleFlow, PulseNotify) that can be forced into each failure mode on demand.

2. Test Categories Covered

  • Happy path — the documented flow works under expected conditions.
  • 5xx — the dependency returns a server error.
  • 429 rate limit — the dependency throttles the caller.
  • Timeout — the dependency hangs or responds after the timeout budget, including the ambiguous case where the outcome is unknown.
  • Malformed payload — a request or response fails schema validation.
  • Duplicate delivery / idempotency — the same operation is triggered twice.

IDCategorySeam Under TestScenarioExpected ResultIdempotency Check

4. Idempotency Verification Method

How every duplicate-delivery test is actually verified

Not by inspecting the response alone — by querying the downstream system of record (SettleFlow’s disbursement ledger, the Claims Case Store, or the sent-message log) to confirm exactly one side effect occurred, regardless of how many requests or events were sent. A test that only checks “the second call also returned 200” without checking for a duplicate side effect has not actually verified idempotency.

5. Exit Criteria

  • 100% of the test cases in Section 3 pass against the sandboxed vendor doubles.
  • Every row in the Error-Handling document’s resilience table (Section 2) has at least one corresponding test case above.
  • All three duplicate-delivery tests (TC-18, TC-19, TC-20) are verified against the downstream system of record, not just the immediate response.
