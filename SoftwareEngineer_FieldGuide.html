Overview & the Working Example

This guide teaches the roughly 20% of software engineering an AI Solution Architect needs — not to write production code by hand, but to direct, evaluate, and approve code an AI system writes on your behalf. You will not be graded on syntax. You will be graded on judgment: can you read a design, spot a missing failure path, reject a pull request for the right reason, and sign a Definition of Done with your name on it and mean it.

Everything below is grounded in a single running example so the ideas stay concrete instead of abstract.

Working Example

Industry: Restaurant operations, multi-location.
Company: Verde Table Co. — a 42-location fast-casual chain.
Feature: the Order Orchestration Service (OOS) — when a customer places an order at a POS terminal, kiosk, or the mobile app, OOS routes each item to the correct kitchen station, keeps a live ticket on the Kitchen Display System (KDS), and notifies front-of-house the moment food is ready.
Why it exists: Verde Table's kitchens currently run on paper tickets hand-sorted by a expediter. During peak lunch service, mis-routed tickets and forgotten allergy holds are the #1 driver of remade orders and refund requests.

Every document in this guide — the design, the module contracts, the coding standards, the review checklist, the test plan, the branching rules, the Definition of Done — is written for this feature. That's deliberate: a design document is only as useful as it is specific.

The Discipline

Why Software Engineering Exists

A single working script is easy. A system that keeps working after the fifth engineer touches it, the traffic doubles, and a kitchen printer starts dropping connections at 12:15pm on a Saturday — that requires discipline. Software engineering is the set of practices that make code predictable under change: change of requirements, change of team, change of load, change of failure conditions.

An AI model can generate correct-looking code for the happy path in seconds. It has no innate stake in what happens when the kitchen printer at Location 17 goes offline mid-shift, or when the same order gets submitted twice because a customer double-tapped "Place Order" on a bad wifi connection. That is exactly the gap an AI Solution Architect exists to close: you supply the engineering discipline the model does not have by default, by directing it toward a design, and by refusing to approve output that skips the parts that are actually hard.

The Core Risk You're Managing

AI-generated code is fluent, which makes it persuasive. Fluency is not correctness. Your job is to separate "this reads like it works" from "this is provably going to work when the network drops a packet during Saturday lunch rush."

The Discipline

Technical Design Documents

A Technical Design Document (TDD) is where thinking happens before code exists, when changing your mind costs a paragraph instead of a rewrite. It forces four questions onto paper: what problem is this solving, what approach did we choose and why, how does data flow through the system, and what could go wrong.

As an architect directing AI-generated code, the TDD is your primary lever. You do not write the implementation — you write (or approve) the design the AI implements against. A vague design produces plausible-but-wrong code every time, because the model will confidently fill gaps with its own assumptions.

TDD SectionQuestion It AnswersWhy an Architect Cares
ContextWhat's broken today, for whom?Prevents solving the wrong problem elegantly.
Chosen ApproachWhat are we building, and what did we reject?Makes trade-offs visible and defensible.
Module BreakdownWhat are the pieces and who owns each one?Sets the contract boundaries AI code must respect.
Data ModelWhat persists, and what are its invariants?Schema mistakes are the most expensive to unwind later.
Main SequenceWhat actually happens, step by step?Reveals timing assumptions and race conditions early.
Risks & Trade-offsWhat could fail, and what did we accept?Turns hidden risk into a documented, owned decision.

The Discipline

Modularity & Separation of Concerns

A module should do one thing and be nameable in a sentence without the word "and." RoutingRuleEngine decides which station an item goes to. It does not also send notifications, write to the database, or format a receipt. When a module's name needs "and" to describe it, it needs to be two modules.

In the OOS design, six modules exist because six distinct responsibilities exist: accepting orders, deciding routing, creating tickets, pushing to kitchen displays, notifying humans, and watching station health. None of them know how to do another's job — they only know each other's contracts.

Why It Matters for AI-Directed Work

When you ask an AI system to "add allergy-hold routing," a well-separated design means the change is contained to RoutingRuleEngine — you can review a 40-line diff instead of auditing the whole service. Poor separation means every feature request touches everything, and every review becomes a full-system re-read.

Size discipline

Files stay reviewable when they stay small. This project's house limits: files target ~300 lines (hard ceiling 500), functions target ~50 lines (hard ceiling 100). A file that crosses the ceiling is a signal, not a crime — the next change to it must split it before adding new logic.

The Discipline

Interfaces & Contracts

A contract is a promise stated in a form the compiler and the reviewer can both check: given these typed inputs, you get this typed output, or one of these named errors — nothing else, nothing silent. Contracts are what let two modules (or two engineers, or an architect and an AI system) collaborate without reading each other's implementation.

// The contract IS the review surface. An architect can approve this
// without reading routeItems' internals — the types are the promise.
export function routeItems(
  order: Order,
  rules: RoutingRule[]
): StationAssignment[];   // throws ValidationError | NoStationAvailableError | RuleConflictError

Three rules make a contract trustworthy:

  1. Inputs are typed and validated at the boundary — malformed input never reaches business logic.
  2. Outputs are typed — no function returns "whatever object happened to be built."
  3. Errors are named, not generic — NoStationAvailableError tells the caller exactly what to handle; a bare Error tells them nothing.

Full signatures for every OOS module are in Document 2 — Module & API Design.

The Discipline

Clean Code & Naming

Code is read far more often than it is written, and AI-generated code is read by you exactly once, under time pressure, deciding whether to approve it. Names carry that entire burden. routeItems tells a reader what happens without opening the function. process or handle tells them nothing — you're forced to read the body to find out, every single time.

The Reviewer's Naming Test

If you can predict what a function does from its name alone, and you're wrong when you read the body — that's not a naming nit, that's a defect. A misleading name is a bug that hasn't been caught yet.

Full naming conventions (casing, file names, error-class suffixes, schema names) are in Document 3 — Coding Standards & Naming Conventions.

The Discipline

Version Control: Branching & Code Review

Version control turns "the code" into "the code, and a complete argument for why every change to it was correct at the time." Branching keeps unfinished work from destabilizing what's shipping. Code review is the human (or architect) checkpoint before an AI-authored change becomes the team's shared reality.

This project uses trunk-based development: short-lived branches, small pull requests, fast review, squash-merge to main. Long-lived branches are where AI-generated code goes stale against a moving design — the longer a branch lives, the more its assumptions drift from the current contract.

Full branch naming, PR size limits, and merge rules are in Document 6 — Branching & Pull-Request Workflow.

The Discipline

The Testing Pyramid

Not all tests are equal in cost. A unit test runs in milliseconds and pinpoints exactly what broke. An end-to-end test runs in seconds-to-minutes, touches real infrastructure, and tells you something broke somewhere in a whole user journey. The pyramid says: write mostly the cheap, precise kind.

Target vs. Actual Test Mix — Codebase-Wide

Target Actual (current sprint)
TierShareLives Here
Unit~70%Pure logic: RoutingRuleEngine, validators, formatters
Integration~20%Service-to-service: gateway → DB, dispatcher → KDS
End-to-End~10%Full order flow, real browser/API against staging

A suite with more E2E tests than unit tests is a process violation — it's slow, flaky, and expensive to maintain. Push assertions down the pyramid whenever the same behavior can be proven cheaper.

Every feature ships with four case types: happy path, failure path, boundary cases, and idempotency. See Document 5 — Unit & Integration Test Plan for all 21 OOS test cases mapped to these tiers.

The Discipline

Technical Debt

Technical debt is a shortcut taken deliberately, with interest that accrues until it's repaid. It is not automatically bad — shipping the OOS pilot to 3 pilot locations with a hardcoded routing table instead of a full rules editor UI is reasonable debt, if it's written down and someone owns paying it back. Undocumented debt is not a shortcut; it's a landmine for the next person, human or AI, who touches that code assuming it's finished.

The AI-Specific Version of This Risk

An AI system asked to "just make the tests pass" will sometimes take the cheapest path: loosen an assertion, mock away a hard case, catch and swallow an exception. Each of those is technical debt wearing a green checkmark. Treat a suspiciously easy fix as a prompt to read the diff more closely, not less.

The Discipline

DRY & SOLID (Lightly)

DRY — Don't Repeat Yourself

Three is the threshold; two is sometimes a coincidence. If the same non-trivial logic (5+ lines) shows up in three places — say, the same order-validation check duplicated in the POS gateway, the kiosk gateway, and the mobile gateway — lift it into one shared function. Duplicated logic means duplicated bugs: fix it in one place, forget the other two.

SOLID, in one line each

SSingle Responsibility — a module has one reason to change. TicketDispatcher changes when ticket-creation rules change, not when notification copy changes.
OOpen/Closed — add behavior by extension, not by editing working code. Adding a new station type should mean adding a rule, not rewriting RoutingRuleEngine.
LLiskov Substitution — a subtype must be usable anywhere its parent type is expected, without surprises. A BackupStation must behave like a Station in every way callers rely on.
IInterface Segregation — don't force a module to depend on methods it never calls. NotificationService shouldn't be handed the full Order object when it only ever needs the ticket ID and customer contact.
DDependency Inversion — depend on an abstraction (NotificationChannel), not a concrete vendor (Twilio SMS), so the vendor can change without rewriting callers.
The Discipline

Error Handling

Design the failure path before the happy path. Every external boundary in OOS — the POS webhook, the KDS WebSocket, the notification provider — must answer four questions in writing: what happens if this fails, does it retry and how, what's the recovery path once retries are exhausted, and which failure modes are explicitly out of scope.

Forbidden — Reject on Sight

try { ... } catch (e) {} — a silent swallow. This is the single most common AI-generated defect: the model makes an error "go away" instead of handling it, because an empty catch block makes tests pass without solving anything. An empty catch block in a reviewed diff is an automatic Blocker, no exceptions.

See the Good vs. Bad Code comparison below, and the full error-handling rules in Document 3 and the review gate in Document 4.

  • Empty catch(e){} — failures vanish silently.
  • No types on order, rules, or the return value.
  • Magic string default "grill" hides a routing decision no one signed off on.
  • == instead of === — a correctness landmine.
  • Allergy holds are never checked — a silent safety gap.

Approve — meets the OOS contract
export function routeItems(
  order: Order,
  rules: RoutingRule[]
): StationAssignment[] {
  if (order.items.length === 0) {
    throw new ValidationError(
      'ORDER_EMPTY',
      `Order ${order.id} has no items to route`
    );
  }

  return order.items.map((item) => {
    const rule = rules.find(
      (r) => r.itemType === item.type
          && r.locationId === order.locationId
    );
    if (!rule) {
      throw new NoStationAvailableError(item.type, order.locationId);
    }
    return {
      itemId: item.id,
      stationId: rule.stationId,
      allergyHold: item.hasAllergyFlag,
    };
  });
}
  • Explicit types on input, output, and every thrown error.
  • No default fallback station — an unroutable item fails loudly instead of going to the wrong place.
  • Allergy flag is carried through explicitly, not dropped.
  • Pure function — no hidden I/O, easy to unit test (see TP-U01–TP-U04).
  • Boundary case (empty order) handled with a named error.

The Architect's Review Lens

When AI-generated code lands in front of you, run it through these seven questions before it runs through anything else. This is the compressed version of Document 4 — the lens you hold up first.

#QuestionWhat a "No" Means
1Does this match the TDD's chosen approach, not a plausible alternative the model preferred?Scope drift — send back to the design, not the code.
2Are all inputs, outputs, and errors explicitly typed?Contract violation — Blocker.
3Is there a test for the failure path, not just the happy path?Incomplete by definition — not shippable.
4Is every catch block doing something — logging, recovering, or rethrowing?Silent swallow — Blocker.
5Can this operation run twice with the same input safely?Idempotency gap — production defect, not a nit.
6Would a new engineer understand this module in one sitting?Readability failure — request simplification.
7Does anything here cross a governance boundary (new dependency, schema change, security posture)?Escalate — do not approve at the implementation level.

Order Orchestration Service — Real-Time Kitchen Ticket Routing & Status Sync
Verde Table Co. · Restaurant Operations Platform · 42 Locations
Document IDOOS-TDD-001Version1.0
OwnerOOS Platform EngineeringStatusApproved for Pilot
Last Updated2026-08-24ClassificationInternal

1. Context

Verde Table Co. runs 42 fast-casual locations. Kitchens currently receive orders as printed paper tickets, hand-sorted by an expediter into station piles (grill, fry, cold, beverage). During peak service (11:30am–1:30pm, 6:00pm–8:00pm), the expediter routinely mis-sorts tickets under load, and allergy modifiers printed in small type are missed. Operations reports that 62% of comped/remade orders in Q2 2026 traced back to a routing or allergy-hold error at the paper-ticket stage, not a cooking error.

The business goal: eliminate manual ticket sorting for the initial pilot cohort of 3 locations, with the design built to scale to all 42 without a rewrite.

2. Chosen Approach

An event-driven Order Orchestration Service (OOS), deployed as a standalone Node.js/TypeScript service, subscribes to order-creation events from all three ordering channels (POS, kiosk, mobile app), applies a per-location routing rule set, creates one ticket per kitchen station touched by the order, and pushes tickets to that station's Kitchen Display System (KDS) client over a persistent WebSocket connection. When kitchen staff mark a ticket ready, OOS notifies front-of-house and, where a phone number is on file, the customer directly.

Option ConsideredVerdictReasoning
Keep paper tickets, add a printer-timestamp audit trail onlyRejectedDoesn't address the root cause — human mis-sorting under load.
Third-party KDS SaaS (rip-and-replace POS integration)Rejected for pilot12+ week integration timeline against 42 heterogeneous POS configs; too slow to validate the hypothesis.
In-house Order Orchestration Service (chosen)ApprovedReuses existing POS webhook events already emitted for receipt printing; ships to 3 pilot locations in one sprint.
Polling-based KDS refresh instead of WebSocket pushRejectedAdds 2–5s of routing latency during peak load exactly when speed matters most.

Verde Table Co. · Restaurant Operations Platform

Each module below has exactly one responsibility. Its interface is its contract: an AI system implementing against this document should never need to guess an input shape, an output shape, or which errors are possible.

1. Order Ingest Gateway

Responsibility: validate and deduplicate inbound order payloads from any channel before they reach business logic.

interface OrderPayload {
  locationId: string;
  channel: 'POS' | 'KIOSK' | 'MOBILE';
  idempotencyKey: string;
  items: Array<{ type: string; modifiers: string[]; hasAllergyFlag: boolean }>;
  customerContact?: string;
}
interface IngestResult { orderId: string; deduplicated: boolean; }

function ingestOrder(payload: OrderPayload): Promise<IngestResult>;
// throws ValidationError        — payload fails schema (missing field, empty items)
// throws IdempotencyConflictError — same key, different payload body

2. Routing Rule Engine

Responsibility: pure function mapping order items to kitchen stations using the active rule set. No I/O.

interface RoutingRule { ruleId: string; locationId: string; itemType: string; stationId: string; priority: number; }
interface StationAssignment { itemId: string; stationId: string; allergyHold: boolean; }

function routeItems(order: Order, rules: RoutingRule[]): StationAssignment[];
// throws ValidationError         — order.items.length === 0
// throws NoStationAvailableError — no rule matches item type + location
// throws RuleConflictError       — two active rules match with equal priority

3. Ticket Dispatcher

Responsibility: persist tickets from station assignments; own ticket state transitions; enforce dispatch-level idempotency.

interface Ticket { ticketId: string; orderId: string; stationId: string; status: 'QUEUED'|'IN_PROGRESS'|'READY'|'DELIVERED'; dispatchKey: string; }

function createTickets(assignments: StationAssignment[], dispatchKey: string): Promise<Ticket[]>;
// throws IdempotencyConflictError — dispatchKey already has tickets (returns existing set instead)
// throws PersistenceError        — DB write failed after retry budget exhausted

function markReady(ticketId: string): Promise<Ticket>;
// throws TicketNotFoundError
// throws InvalidStateTransitionError — e.g. DELIVERED → READY

4. KDS Sync Gateway

Responsibility: maintain WebSocket connections to kitchen display clients; push tickets; redeliver on reconnect.

function pushTicket(ticket: Ticket, stationId: string): Promise<void>;
// throws StationUnreachableError — no active connection; caller queues for redelivery
// throws AckTimeoutError         — no client ack within 5s (default timeout)

5. Notification Service

Responsibility: notify front-of-house and, if contact info exists, the customer when a ticket reaches READY.

function notifyReady(ticket: Ticket, customerContact?: string): Promise<void>;
// throws NotificationDeliveryError — provider failure after 3 capped retries (logs to dead-letter, does not throw further)

6. Station Health Monitor

Responsibility: track per-station heartbeats; mark stations OFFLINE; signal the Routing Rule Engine to prefer backup stations.

interface HealthStatus { stationId: string; state: 'ONLINE'|'DEGRADED'|'OFFLINE'; lastHeartbeatAt: string; }

function checkHealth(stationId: string): Promise<HealthStatus>;
// never throws — absence of heartbeat data returns state: 'OFFLINE'

2. Types

  • TypeScript strict mode is on for the whole service. tsc --noEmit must pass before merge.
  • any requires a one-line comment explaining why no narrower type exists. Bare any is a review Blocker.
  • Every exported function has an explicit return type — never inferred silently across a module boundary.

3. Validation

  • Every HTTP route validates its body, query, and route params with a Zod schema before touching business logic.
  • Malformed input is rejected with 400 and a machine-readable error code (e.g. ORDER_EMPTY) — never a bare 500.

4. Comments

Default to no comments. Names should make the "what" obvious. Write a comment only when it explains a non-obvious why — a hidden constraint, a workaround for a specific upstream bug, a subtlety that would surprise the next reader. Never restate what the code already says.

5. Error Handling

  • No empty catch blocks, ever. Every catch either recovers, logs and rethrows with a stable error_class, or routes to a dead-letter path.
  • Catch specific error classes, not bare Error or Exception, wherever the failure mode is known.
  • Every outbound call (DB, WebSocket, notification provider) has an explicit timeout — never unbounded.

6. File & Function Size

Soft target 300 lines / file, 50 lines / function. Hard ceiling 500 / 100. Crossing the ceiling means the next change must split the unit before adding new logic.

7. Logging

Structured JSON only, to stdout. Every log line includes timestamp, level, service, event, correlation_id, outcome, and — on failure — error_class. No unstructured console.log strings in a production code path.

1. Model — Trunk-Based Development

main is always deployable. Feature work happens on short-lived branches (target: merged within 2 days) and lands via squash-merge. No long-running develop branch.

2. Branch Naming

PrefixUseExample
feature/New capabilityfeature/OOS-108-allergy-hold-routing
fix/Bug fixfix/OOS-115-kds-reconnect-loop
chore/Tooling, deps, non-behavioral cleanupchore/upgrade-zod-v4

3. Branching Diagram

Feature branches (berry) squash-merge above the line; fix branches (cherry) below. Release tags mark deployable points.

4. PR Size & Review Rules

RuleThreshold
Soft PR size cap~400 changed lines; larger PRs require a split rationale in the description
Required approvals1 approval from the module's designated owner, minimum
CI gates before mergetsc --noEmit, unit + integration test suite, lint, secret scan — all green
Merge strategySquash-merge only; commit message summarizes the "why"
Stale branch policyBranches open >5 days are rebased or closed — AI-authored branches drift fastest against a moving contract

5. Commit & PR Message Convention

Subject line states the "why," not the "what" (the diff already shows what changed). Body links the ticket and, for AI-assisted changes, notes any logged assumptions.

fix(kds-gateway): redeliver queued tickets on station reconnect

Stations going OFFLINE mid-shift were losing queued tickets on
reconnect, forcing a manual re-print. Redelivery now replays the
station's pending queue on ACK of a new connection.

Ref: OOS-115
Tests: TP-I03
