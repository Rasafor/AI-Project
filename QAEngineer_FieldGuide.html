QA Engineer Field Guide

The 20% of quality assurance an AI Solution Architect must master — not to execute tests by hand, but to direct, evaluate, and approve the tests and quality evidence that AI systems and QA engineers generate on your behalf. Every document in this guide is written against one concrete initiative so you can see the discipline applied, not just defined.

Industry: Insurance Initiative: ClaimsIQ — AI-Assisted FNOL Intake & Triage Carrier: Meridian Mutual Insurance Release: 3.2

Why this guide exists

As an AI Solution Architect you will rarely write a test case yourself. You will review one an AI assistant wrote, decide whether it is trustworthy, and put your name on the recommendation that follows it. That is a different skill from execution — it is judgment. This guide teaches the vocabulary and the checklist behind that judgment, then hands you seven real deliverables built around a single believable initiative so the vocabulary has somewhere to live.

The initiative

Meridian Mutual is piloting ClaimsIQ: an AI layer that ingests First Notice of Loss (FNOL) submissions from web, mobile, and phone-transcript channels, extracts structured claim data, classifies severity, screens for fraud signals, and straight-through processes small glass-only claims.

How to use this page

Read QA Foundations once. Then use Search or Ask the guide to jump straight to what you need when reviewing a real deliverable. Every document below is individually downloadable as a styled HTML file, a print-ready PDF, and (where tabular) a CSV.

What "approve" means here

Approval is not "tests are green." It is: every requirement traces to a test, negative and boundary and idempotency paths exist alongside the happy path, severity and priority are justified separately, and the ship/no-ship call is backed by named evidence.

QA Foundations: the 20% that matters

Software is probabilistic while it's being built and must become deterministic before it ships. Quality assurance is the discipline that closes that gap: it turns "I think this works" into "here is the evidence this works, and here is what we know it does not handle." An AI Solution Architect does not need to run every test — but does need to recognize when evidence is thin, when a happy-path-only suite is being presented as "done," and when a severity label has been inflated or deflated to make a release look safer than it is.

Test strategy vs. test plan vs. test cases

These three documents are frequently used interchangeably by non-practitioners — and that confusion is itself a review red flag. They sit at different altitudes:

DocumentAltitudeAnswersChanges how often
Test StrategyProgram-levelWhat quality means for this product; which levels and types of testing we run and why; standing entry/exit rules.Rarely — roughly once per product line
Test PlanRelease-levelWhat is in and out of scope this cycle; schedule; environments; who does what; this cycle's suspension criteria.Every release or sprint
Test CasesFeature-levelThe literal steps and expected results that prove one requirement, one path, one condition.Continuously, as features change

An AI assistant asked for "the test plan" will sometimes hand back test cases, or hand back a strategy dressed up as a plan. Check the altitude before you check the content.

The testing pyramid

Automated test investment should be heaviest at the bottom (fast, cheap, deterministic) and lightest at the top (slow, expensive, occasionally flaky). A suite that inverts this — more end-to-end tests than unit tests — is a maintenance liability wearing a green checkmark.

TierTarget shareLives inClaimsIQ example
Unit~70%Pure logic, formatters, extractors, scoring functionsVIN-format validator; severity-score rounding rules
Integration~20%Service-to-service, DB, mocked external APIsFNOL service → fraud-signal service → adjuster-queue assignment
End-to-end~10%Real browser / API flows against stagingFull FNOL submission through auto-approval and payment

Functional vs. non-functional testing

Functional testing asks "does it do the right thing?" — given this input, is the output correct. Non-functional testing asks "does it do the right thing well enough, safely enough, and under real conditions?" AI-generated test suites disproportionately over-invest in functional happy paths and under-invest in non-functional testing, because non-functional targets require someone to pick a number. That number is where the architect's judgment is required.

Non-functional dimensionClaimsIQ targetWhy it's numeric, not vibes
PerformanceP95 FNOL-to-triage latency < 12sAbove 12s, the mobile app's own timeout fires and the claim silently drops.
Availability99.5% during 7am–9pm local, graceful manual fallback otherwiseBelow this, state insurance SLAs for claim acknowledgment are at risk.
AccessibilityWCAG 2.1 AA on all FNOL intake surfacesLegal exposure and genuine exclusion of policyholders using assistive tech.
Security / privacyZero PII in plaintext logs; 100% of exports redactedA single unredacted export is a reportable incident, not a "minor" defect.
Review flag

If a non-functional "test" has no number attached — "the system should be fast," "the form should be accessible" — it is not a test yet. It's a wish. Send it back for a measurable target before you accept it as coverage.

Given / When / Then acceptance tests

Behavior-driven acceptance tests are written in a fixed three-part grammar so that a business stakeholder, a QA engineer, and an AI generating test code can all read the same sentence and agree on what "correct" means:

ClauseStatesClaimsIQ example
GivenThe starting state / preconditionsGiven a policy in good standing with a $750 windshield-only glass claim
WhenThe action under testWhen the policyholder submits FNOL through the mobile app
ThenThe observable, checkable outcomeThen the claim is auto-approved, a single payment is issued, and an audit entry is written with model version and reason code

Given/When/Then is used throughout the Test Cases document below for every acceptance test.

Positive, negative, boundary, and idempotency cases

A requirement is not covered by one test — it's covered by a family of tests that probes the requirement from every angle an adversarial user or a flaky network could produce.

Positive (happy path)

Valid input, expected preconditions, expected outcome. Proves the feature works when everything goes right. Necessary but never sufficient.

Negative

Invalid input, missing preconditions, unavailable dependency. Proves the system fails safely instead of silently or destructively.

Boundary

Values exactly at, one below, and one above a threshold. Off-by-one errors live here — e.g. a claim at exactly $1,500.00.

Idempotency

The same operation, submitted twice (retry, duplicate webhook, double-tap), must produce the same end state with no duplicate side effect. Non-negotiable for anything that moves money.

Review flag

A test suite with only positive cases is the single most common defect in AI-generated QA evidence. If you see 20 passing tests and all 20 are happy-path, treat requirements coverage as effectively zero until negative, boundary, and idempotency siblings exist.

Traceability to requirements & coverage

Traceability is the explicit link from a requirement to the test(s) that prove it. Coverage is the resulting measurement — what percentage of requirements have at least one passing test, and (separately, more precisely) what percentage of code branches or paths are exercised. The two numbers are not interchangeable: 100% code coverage with zero negative-path assertions is easy for an AI to produce and tells you almost nothing about safety.

The rule this guide enforces throughout: every requirement has at least one test, and every test traces back to a requirement. A test with no requirement behind it is "orphan" — it may be testing something nobody asked for, or worse, papering over a requirement nobody wrote down. See the Requirements Traceability Matrix for the worked example.

Defect severity vs. priority

These are two independent axes, and collapsing them into one is the second most common defect in AI-generated defect logs.

SeverityPriority
Question it answersHow badly is the system broken?How soon must it be fixed?
Who typically sets itQA / the engineer who found it, from technical impactProduct / release owner, from business urgency
ExampleA typo in a footer copyright year — Severity: Low...but it ships to 40,000 renewal letters tomorrow — Priority: P1
Independent exampleA crash in an admin tool used twice a year — Severity: Critical...but next use is in 8 months — Priority: P4
Review flag

"Every defect is Critical / P1" is not rigor, it's the absence of triage. If a defect log has no spread across severities, the triage step was skipped — push back before you sign off on the Test Summary Report.

Regression & exploratory testing

Regression testing re-runs previously-passing tests after a change to catch anything the change broke that nobody was looking for. It should be automated and it should run on every build. Exploratory testing is structured, time-boxed, human-driven investigation with no fixed script — a skilled tester (or a well-prompted AI red-team pass) actively trying to break the system in ways the written test cases didn't anticipate. Both are required; neither substitutes for the other. ClaimsIQ's exploratory charter includes deliberately feeding the FNOL narrative extractor ambiguous, contradictory, and adversarial free-text claim descriptions.

Shift-left

Shift-left means moving quality activities earlier in the lifecycle — writing acceptance tests before the code that satisfies them, validating a requirement's testability at design time, running static analysis and contract checks on every commit rather than at the end of a sprint. The later a defect is caught, the more it costs: a requirement ambiguity caught in review costs a conversation; the same ambiguity caught in production costs an incident, a defect report, a fix, a retest, and (for ClaimsIQ) potentially a regulatory disclosure if it affected a payment decision.

The architect's review lens

When an AI assistant hands you a test suite, a defect log, or a ship recommendation, run it through this checklist before your name goes anywhere near "approved."

#QuestionWhy it matters
1Does every requirement have at least one test, and does every test trace to a requirement?Catches gaps and orphan tests in one pass
2Are negative, boundary, and idempotency cases present, or is this happy-path only?The most common gap in generated suites
3Do non-functional requirements carry a measurable number and an actual measured result?Separates a test from a hope
4Are severity and priority both present, independently justified, and not uniformly Critical?Signals real triage happened
5Could this test suite pass while the feature is actually broken?The false-confidence check — e.g. a mocked dependency that never exercises the real failure mode
6Is the ship/no-ship recommendation explicit, and is the evidence behind it named and checkable?"Looks fine" is not a recommendation an architect can stand behind
7Are known, deferred, or accepted risks stated out loud, or only the passing tests?What's omitted is often more important than what's shown

1. Purpose & scope

This strategy governs all testing for the ClaimsIQ program: the AI-assisted First Notice of Loss (FNOL) intake, extraction, severity triage, fraud-signal screening, and straight-through payment capability being rolled out to Meridian Mutual's personal auto line. It applies across releases; release-specific scope, schedule, and staffing live in the Test Plan.

In scope: web, iOS/Android app, and phone-transcript FNOL channels; the AI extraction and severity-classification services; fraud-signal screening; adjuster-queue assignment; straight-through payment for qualifying glass claims; the audit/logging layer. Out of scope for this strategy: the legacy mainframe policy system of record (tested under its own program) and third-party SIU (Special Investigations Unit) case-management tooling, which is validated only at the integration boundary.

2. Quality objectives

  • No claim decision (approval, denial, fraud flag) is made without a human-overridable, audited AI output.
  • No policyholder is charged, paid, or denied twice for the same loss event, regardless of retries or duplicate submissions.
  • Every requirement in the current release has at least one automated test; non-functional requirements carry a measured, numeric result.
  • FNOL intake surfaces meet WCAG 2.1 AA; no policyholder is excluded by assistive-technology incompatibility.

3. Testing levels & types

ClaimsIQ follows the standard testing pyramid (see Foundations → Testing pyramid): ~70% unit, ~20% integration, ~10% end-to-end. Investment scales with blast radius:

Risk tierExamplesRequired coverage
High — irreversible / financialAuto-approval payment, fraud-flag suppression, PII handlingUnit + integration + E2E + idempotency + security review
Medium — internal workflowAdjuster-queue assignment, severity triageUnit + integration
Low — display / formattingClaim status labels, adjuster dashboard formattingUnit only

4. AI-specific testing considerations

ClaimsIQ's core novelty — and risk — is that several decision points are made by a model rather than deterministic code. The strategy treats these as first-class test targets, not an exception to normal QA:

Contract testing on model I/O

The extraction and severity-classification services expose a typed contract (structured JSON out, regardless of model version). Contract tests run on every model or prompt change, independent of the underlying model provider.

Golden-set regression

A held-out set of 400 real (de-identified) historical FNOL narratives with adjuster-confirmed severity labels is re-scored on every model change; agreement must stay ≥90% or the change is blocked.

Human-override capture

Every adjuster override of an AI severity call is logged with before/after values and feeds the model-feedback backlog — tested as a functional requirement (REQ-09), not just a data-science nice-to-have.

Adversarial / exploratory red-team

A scheduled exploratory charter feeds ambiguous, contradictory, and adversarial narrative text to the extractor and fraud screen to probe for prompt-injection and misclassification risk.

5. Entry & exit criteria (standing)

Criteria
EntryRequirements traced in the RTM; test environment matches the release's dependency versions; test data is synthetic or de-identified only.
Exit100% requirements coverage; zero open Critical defects; open High defects have an accepted-risk sign-off; all NFR targets measured and met or explicitly waived; ship/no-ship recommendation issued.

6. Environments & tools

Unit and integration tests run in CI on every commit against containerized dependencies. End-to-end tests run nightly against a dedicated ClaimsIQ staging environment seeded with synthetic policyholder data. Tools: Jest/Vitest (unit), a contract-testing harness for model I/O, Playwright (E2E, browser and mobile web), k6 (performance/load), axe-core (accessibility), and a manual SIU-sandbox pass for fraud-signal review pending automated coverage.

7. Roles & responsibilities

RoleResponsibility
QA LeadOwns strategy and plan; gatekeeps exit criteria
SDETBuilds and maintains automated suites across all three pyramid tiers
AI Solution ArchitectReviews and approves AI-specific test design, traceability completeness, and the final ship/no-ship recommendation
Claims SME / Adjuster liaisonValidates severity and fraud-signal test oracles against real claims judgment
Deviation note

Per the 12-factor production-readiness principle, any deviation from this strategy (e.g. skipping a testing level for a specific feature) must be logged in that feature's directive with reasoning — not silently absorbed into "we ran out of time."

5. Environment & test data

All testing runs against the ClaimsIQ staging environment, isolated from production policy and payment systems. Test data is 100% synthetic: policyholder identities, VINs, and loss narratives are generated or drawn from a de-identified historical corpus with names, addresses, and policy numbers replaced. No production PII enters the test environment at any point — this is a hard gate, not a preference.

7. Suspension / resumption criteria

Testing is suspended if: the staging environment's fraud-signal model diverges from the production candidate build, or if a Critical defect blocks more than 20% of planned test cases from executing. Resumption requires a fix or a documented workaround, re-verified by the QA Lead before execution continues.

Worked example

DEF-0042 — Duplicate payment issued on webhook retry within 400ms window

Severity: Critical Priority: P1
StatusClosed — Fixed & Verified
Reported ByDevon Park, Senior SDET
Date Reported2026-08-14
Environment / BuildClaimsIQ staging, build 3.2.0-rc4, Payment Svc v1.9.2
Related Req / TCREQ-12 / TC-021
Steps to Reproduce 1. Submit an eligible glass-only claim ($900) for straight-through auto-approval.
2. Simulate a payment-service response delay > the client's 5s timeout.
3. Allow the mobile client to auto-retry the payment POST using the same idempotency key, but fire the retry at exactly 400ms after the original request (before the original request's DB transaction commits).
4. Inspect the payments table for the claim.
Expected ResultExactly one payment row exists for the claim, regardless of retry timing.
Actual ResultTwo payment rows were created for the same claim, both for $900 — the policyholder was paid twice.
Evidencecorrelation_id=8f2a...c19e appears on both payment rows; payment_svc logs show two "processing" states for idempotency_key=k-88213 with a 400ms gap, both passing the pre-insert existence check before either row committed.
Root CauseThe idempotency check was "check-then-insert": a SELECT for the existing key followed by an INSERT, not wrapped in a single atomic operation. Two concurrent requests within the same ~400ms window could both pass the SELECT before either INSERT committed — a classic time-of-check-to-time-of-use (TOCTOU) race condition.
Fix SummaryReplaced check-then-insert with a single atomic upsert: a unique constraint on idempotency_key plus INSERT ... ON CONFLICT DO NOTHING, with the conflicting request reading back and returning the winning row's result instead of racing to insert its own.
VerificationTC-021 re-run under a 500-iteration concurrent-retry load test (k6): zero duplicate payments across all iterations. Fixed in build 3.2.0-rc6, verified 2026-08-16.
